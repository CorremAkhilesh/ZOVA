# Security findings — backend (Step 20, Part A)

Scope: every REST route and Socket.IO event of the API (OWASP ASVS L2, OWASP API Security Top 10
2023): authentication, authorization (IDOR/BOLA, function-level), input validation, rate limits,
error messages, logs, test-only surface. The route-by-route matrix is in `docs/security-routes.md`.

Severity: **High** (exploitable now, serious impact) · **Medium** (exploitable with a precondition,
or a missing defence layer) · **Low** (defence in depth, small impact) · **Info** (observation,
by design). Status: **fixed** (with a test that fails without the fix) · **accepted** (by design,
reason given) · **open**.

## Checked and found sound (no change needed)

- **Authentication on every route.** All 133 production routes except `health`, `ready`,
  `otp/request`, `otp/verify`, `logout` and `not-me` answer `401` without a session (sweep in
  `route-matrix`, and again on a production build in `production-surface`). Sessions are resolved
  in `onRequest`, before body parsing and validation. Every socket event re-checks the session.
- **Authorization / IDOR (BOLA).** Someone else's chat, message, reaction, star, pin, poll, view-once
  message, file, upload, folder, draft, scheduled message, session, push device, wallpaper and
  report target answers `404` — the same as a missing one — and **the whole database is unchanged
  afterwards** (`idor-chats`, `idor-messages`, `idor-media`, `idor-account` snapshot every
  collection before and after). Cross-chat confusion (my chat id + someone else's message id),
  forwarding out of or into a chat I am not in, quoting a message from another chat, and attaching
  another user's upload to my message or scheduled message are all refused.
- **Function-level authorization.** Admin routes answer `403` to non-admins; group admin actions
  answer `403` to plain members; sender-only actions (edit, delete for everyone, message info, close
  poll) answer `403` to other members.
- **No leakage across chats.** Chat list, `/v1/sync`, message search (also with a `chatId` filter),
  stars and the media gallery never include chats the caller is not in. Invite previews show the
  group's name, photo and size, never messages. Profiles apply privacy settings and never show
  email addresses.
- **OTP.** 6 digits, 10 min TTL, 5 wrong attempts per code then locked, codes hashed, 60 s resend
  cooldown, 5 codes per email per hour, per-IP hourly limit (rejected domains count), 20 requests
  per minute per IP on both OTP routes. Identical answers for existing and new allowed emails, on
  request and on a wrong code (`auth`, `auth-hardening`).
- **Session fixation.** Sign-in always issues a fresh token; a planted or pre-existing cookie is
  never adopted (`auth-hardening`).
- **Cookie flags (production).** `__Secure-zuvo.session_token`, `Secure`, `HttpOnly`,
  `SameSite=Lax`, `Path=/`, no `Domain` (host-only), `Max-Age` 7 days (`production-surface`).
- **7-day absolute expiry.** No sliding refresh (`disableSessionRefresh`); after 7 days `401
  SESSION_EXPIRED` and the socket closes at expiry (`auth-security`, `realtime-sessions`).
- **Logout everywhere / deactivation.** Revoking one device, "sign out other devices", logout,
  "This wasn't me" and admin deactivation all delete the sessions and disconnect live sockets
  (`realtime-sessions`, `auth-hardening` for "This wasn't me").
- **Socket handshake.** `Origin` must be ours (`null` and other sites refused), the session cookie
  is required and checked like REST (`realtime-sessions`).
- **Test-only routes.** All `/v1/test/*` routes and `/docs` are absent from a `NODE_ENV=production`
  build (not in the route table, `404` when called) (`production-surface`). With `NODE_ENV=test`,
  env validation refuses any database not named `zuvo_test_*`.
- **Safe errors.** `5xx` answers are generic (`INTERNAL_ERROR`, request id only); validation errors
  list paths and messages, never the submitted values; socket failures log only error names/codes,
  never message text (`error-handler`, `realtime-logging`).

## IDOR test results (`backend/src/security-tests/idor-*.test.ts`)

Each file signs in three people (Asha owns the chats, Bharat is a member, Chetan is an outsider),
creates the resources, then has the wrong person try every route and socket event on them. Every
collection is snapshotted before and after (only `session`/`verification` and the debounced group
list-order stamp `lastActivityAt` are left out), and the snapshots must be identical.

Observations from writing them (no vulnerability):

- `GET /v1/chats/:id/media` requires `?tab=media|docs|links`; without it the answer is `400`
  (validation runs before the membership check, which is fine: the `400` says nothing about the chat).
- Creating a folder with a chat id the caller is not in is refused with `400` rather than `404`;
  the folder is not created and the chat id is not echoed.
- A group's default lets every member pin messages; the test sets `pinMessages: admins` to check
  the admin-only path (`403`).
- Bursts on rate-limited routes: see B12.

## Origin-check decision (B2)

- **Refused (`403 FORBIDDEN`)** for `POST`/`PUT`/`PATCH`/`DELETE`: an `Origin` that is not `APP_URL`
  or one of `CORS_ORIGINS` (compared as origins), `Origin: null`, or — with no `Origin` — a
  `Sec-Fetch-Site` of `cross-site` or `same-site`.
- **Allowed:** our own origins; requests with neither header (curl, scripts, health probes, server
  to server — no browser cookies involved); all `GET`/`HEAD`/`OPTIONS` (CORS protects reads).
- Runs in `onRequest` before authentication and parsing, on every route including Better Auth's
  typed wrappers and the public OTP routes. Playwright/E2E are unaffected: the browser's `Origin` is
  the app origin (`APP_URL` = `CORS_ORIGINS` in `e2e-server.ts`); backend tests either send
  `Origin: http://localhost:5173` (`headers()` helper) or no `Origin`.
