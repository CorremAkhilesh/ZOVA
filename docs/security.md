# Security

How the app protects people's messages, files and accounts: the threat model, the protections per
area, the findings of the Step 20 review and what is deliberately out of scope.

Related: `docs/security-findings-backend.md` (route-by-route authorization review),
`docs/security-routes.md`, `infra/nginx/README.md`, ADRs in `docs/adr/`.

---

## 1. Threat model

### What we protect (assets)

| Asset                                               | Where it lives                          |
| --------------------------------------------------- | --------------------------------------- |
| Message content, polls, drafts, reactions           | MongoDB (server-side history, ADR 0002) |
| Media (photos, videos, voice, documents)            | Media disk behind `StorageDriver`       |
| Accounts, profiles, privacy settings                | MongoDB                                 |
| Sessions (7-day absolute) and OTP codes             | MongoDB + Redis (codes hashed)          |
| Web Push subscriptions (capability URLs)            | MongoDB                                 |
| Secrets (`AUTH_SECRET`, SMTP, VAPID, DB/Redis URLs) | Env files on the server, GitHub Secrets |
| Availability (disk, queues, rate limits)            | Server, Redis                           |

### Who we defend against (actors)

- **Outsiders** on the internet: no account (only `@corremadvisory.com` addresses can sign in).
- **Signed-in colleagues** trying to read or change what is not theirs (IDOR, broken authorization).
- **Malicious content**: a crafted file, link or message aimed at another user's browser (XSS,
  content sniffing, clickjacking) or at our server (SSRF, decompression bombs, path traversal).
- **Network attackers** between the browser and the server (TLS, HSTS).
- **Supply chain**: a vulnerable or compromised npm package; a secret committed to git.

### Trust boundaries

```
Browser (app, service worker)
   │  HTTPS (HTTP/2) — CSP, HSTS, cookies httpOnly/Secure/SameSite=Lax
   ▼
Nginx + Certbot (shared company server) — TLS, static app + generated security headers
   │  proxies /v1 and /socket.io on the same origin
   ▼
API (Fastify + Socket.IO) — authn on every route/event, authz per resource, Zod on every input
   ├──► MongoDB Atlas (TLS, per-environment database)
   ├──► Redis (password, internal only)
   ├──► Media disk (random keys, never user file names)
   ├──► SMTP (Hostinger, TLS) — OTP and new-login emails
   ├──► Web Push services (VAPID; payloads encrypted to the device)
   └──► The internet, for link previews only — behind the SSRF guard
```

## 2. Protections per area

### Auth, OTP and sessions

- Email + 6-digit OTP only; the organization domain is checked (exact match) before any code is
  made, again at verify and at session creation.
- Codes are stored hashed, 10 min TTL, 5 attempts, 60 s resend cooldown, 5 codes/email/hour, per-IP
  limit; same response whether an allowed email has an account.
- Session cookie `__Secure-zuvo.session_token` in production: host-only, `httpOnly`, `Secure`,
  `SameSite=Lax`; 7 days absolute (no refresh). Better Auth's origin check (`trustedOrigins`) plus
  Lax block cross-site writes (CSRF). Sessions can be listed and revoked; new-login email with
  "This wasn't me" revokes all of them. Deactivation revokes all sessions at once.
- Sockets: authenticated from the session cookie; the `Origin` header is checked against the
  allow-list (cross-site WebSocket hijacking).

### Authorization

Every route and socket event checks the session and membership of the chat / ownership of the
resource. See section 7 and `docs/security-findings-backend.md`.

### Transport and security headers

One source of truth: `shared/config/src/security-headers.ts`.

| Where                            | How the headers are applied                                                            |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| API (`/v1/*`)                    | `onSend` hook in `backend/src/plugins/security.ts`, on every response incl. errors     |
| Web app in production            | Nginx includes `infra/nginx/security-headers.conf`, generated by `pnpm security:nginx` |
| `vite preview` (E2E), `vite dev` | Vite plugin `frontend/src/lib/security-headers-plugin.ts`                              |

A backend test fails if the Nginx snippet is out of date; `frontend/e2e/csp.spec.ts` runs the built
app (sign-in, chat list, a conversation with a photo, settings, help) and fails on any CSP violation.

**Web app CSP (production):**

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:;
media-src 'self' blob:; font-src 'self'; connect-src 'self'; worker-src 'self'; manifest-src 'self';
frame-src 'none'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none';
upgrade-insecure-requests
```

- **Scripts:** our own files only. No inline script, no `eval`. The pre-paint theme/accent script is
  `frontend/public/theme-init.js`, which also sets Zod to `jitless` before the bundle loads (Zod
  otherwise probes `new Function('')` when the first schema is built, a CSP violation). The
  offline page loads `public/offline.js` instead of an `onclick` attribute.
- **Styles:** `'unsafe-inline'` is needed because Radix (react-remove-scroll), Sonner and
  react-easy-crop insert `<style>` elements at runtime. Inline CSS cannot run script, and React
  escapes all user text, so a CSS injection would first need an HTML injection that `script-src`
  already stops. (React's `style={…}` props use the CSSOM and are not affected by CSP.)
- **Images:** `blob:` for local previews before upload and for view-once files, `data:` for blur
  placeholders and the SVG wallpaper patterns. **Media:** `blob:` for voice recordings.
- **Connections:** same origin only. CSP3 `'self'` matches `wss:` to the same host (Socket.IO). Link
  previews and their pictures are fetched by our server (below), never by the browser.
- `upgrade-insecure-requests` is production only; `vite preview` sends the same policy without it
  (it serves plain HTTP on 127.0.0.1). `vite dev` also allows inline scripts, for React Refresh.

**API CSP:** `default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` (+
`upgrade-insecure-requests` in production). Media files keep their own stricter
`default-src 'none'; sandbox; frame-ancestors 'none'`. The API docs page (`/docs`, non-production
only) is the one response without a CSP.

**Other headers (app and API):**

| Header                              | Value                                                                                                                                                                                                                                                                                                    |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Strict-Transport-Security`         | `max-age=63072000; includeSubDomains` (production only; no `preload`)                                                                                                                                                                                                                                    |
| `X-Frame-Options`                   | `DENY`                                                                                                                                                                                                                                                                                                   |
| `X-Content-Type-Options`            | `nosniff`                                                                                                                                                                                                                                                                                                |
| `Referrer-Policy`                   | `same-origin` (chat URLs never leak to other sites)                                                                                                                                                                                                                                                      |
| `Permissions-Policy`                | `microphone=(self), camera=(self), display-capture=(), geolocation=(), payment=(), usb=(), serial=(), hid=(), midi=(), accelerometer=(), gyroscope=(), magnetometer=(), xr-spatial-tracking=(), publickey-credentials-get=(self), fullscreen=(self), picture-in-picture=(self), screen-wake-lock=(self)` |
| `Cross-Origin-Opener-Policy`        | `same-origin`                                                                                                                                                                                                                                                                                            |
| `Cross-Origin-Resource-Policy`      | `same-origin` (app, API and media are one origin)                                                                                                                                                                                                                                                        |
| `Origin-Agent-Cluster`              | `?1`                                                                                                                                                                                                                                                                                                     |
| `X-Permitted-Cross-Domain-Policies` | `none`                                                                                                                                                                                                                                                                                                   |

No `Cross-Origin-Embedder-Policy`: the app needs no cross-origin isolation, and COEP would only add
breakage risk. Production is same-origin (`API_URL` = `APP_URL`); a split app/API host would need
CORP `same-site` and a `connect-src` entry.

### Uploads and media

- Type decided by **magic bytes** (`file-type` / own signatures), never by name or declared type;
  allow-lists per kind (`backend/src/media/validate.ts`). Executables and scripts are refused by
  signature and by extension.
- Limits: `MEDIA_MAX_FILE_MB` (default 1024) per file, pictures 100 MB, voice 64 MB and
  `VOICE_MAX_SECONDS`, avatars 5 MB, wallpapers 10 MB, 8 MB per upload chunk; checked before bytes
  move and again while they arrive. New uploads are refused above 90 % disk use (`507 STORAGE_FULL`).
- Pictures (photos, avatars, group photos, wallpapers, video posters, link-preview images) are
  decoded with a pixel limit and **re-encoded to WebP**, which strips EXIF/GPS and anything hidden.
- Storage keys are random (`ab/cd/<32 hex>`), validated by a strict pattern and resolved inside the
  root (path traversal). User file names are never used on disk; they only appear, sanitized, in
  `Content-Disposition`.
- Serving: only through the API after the membership check, with 15-minute HMAC-signed links;
  `Content-Type` is the verified type, `X-Content-Type-Options: nosniff`, and a sandbox CSP.
  **Documents are always `attachment`**; text formats that a browser could run (HTML, SVG, XML, JS,
  CSS) are stored as `application/octet-stream`. Only verified images, video and audio are inline.
  Byte ranges work (seek in audio/video).

### Link previews (SSRF)

`backend/src/link-preview/` (ADR 0006): only `http`/`https`, no credentials in URLs, ports 80/443 or
≥ 1024; local host names refused; DNS resolved by us and **every** address checked (private,
loopback, link-local incl. `169.254.169.254`, CGNAT, multicast, reserved, NAT64, Teredo, IPv4-mapped
and 6to4 embedded addresses); the socket is **pinned to the checked address** (no DNS rebinding);
redirects are re-checked hop by hop (max 3); 5 s deadline, 3 s connect timeout, 1 MB page / 5 MB
image cap counted after decompression. Pictures are re-encoded to WebP by our server and served
from our origin, so the browser never contacts the linked site.

### Push

VAPID keys per environment; payloads are encrypted to the device by the Web Push protocol; message
previews in notifications follow the user's setting (never shown for locked chats or with app lock). Subscription endpoints and keys are redacted
from logs.

### Logging

pino with redaction of cookies, authorization headers, OTPs, PINs, tokens, email content, push keys
and all secret env values (`backend/src/lib/logger.ts`); covered by
`backend/src/security-tests/log-redaction.test.ts`. Slow-query logs carry the query shape, never
values.

### Secrets

Only in env files on the server and GitHub Secrets; `.env.example` lists every variable with no
values. `MAIL_FROM` must equal `SMTP_USER` (checked at startup). Test-only routes exist only with
`NODE_ENV=test` (`backend/src/security-tests/production-surface.test.ts`). CI runs gitleaks over the
**full git history** (`fetch-depth: 0`) with `.gitleaks.toml` (default rules + one documented public
example key).

### Dependencies

Exact versions, committed lockfile, `onlyBuiltDependencies` allow-list for install scripts. CI fails
on any High/Critical `pnpm audit` advisory. Current Moderate/Low advisories are listed below.

### Backups

Planned with the deploy steps (CLAUDE.md §3a, `docs/runbooks/vps-checklist.md`): daily backups of the database and the media folder, and an alert email above 80 % disk use.

## 4. Out of scope (deliberately)

- **End-to-end encryption.** Messages and media are encrypted in transit (TLS) and readable by the
  server, so every device can sync full history (ADR 0002). E2E "secret chats" are **v2**.
- **A compromised device or browser** (malware, a shared unlocked computer, a malicious extension).
  The chat-lock PIN and the 7-day session limit reduce, but cannot remove, that risk.
- **Server operators.** Correm's IT/server team can access the server, database and media folder, as
  the in-app privacy note (Help → Privacy) says.
- **Denial of service at network scale** — left to the hosting network; the app has rate limits and
  disk guards only.
- **Physical security and backups' storage security** of the company server.

## 7. Backend authorization review

Route by route, every REST route and Socket.IO event was checked for authentication, authorization
(IDOR), input validation, rate limits and safe errors. Details: `docs/security-findings-backend.md`;
the per-route table (auth, authorization rule, rate limit, tests): `docs/security-routes.md`.

- **Inventory:** 133 production routes, 8 test-only `/v1/test/*` routes, 9 client → server socket
  events. A guard test fails if a route or event is added or removed without updating the table.
- **Sweeps over every route** (`backend/src/security-tests/route-matrix.test.ts`): 401 without a
  session (unless public), 403 for a cross-site request on every state-changing method, 400/404 for
  malformed ids.
- **IDOR tests per resource** (`idor-chats`, `idor-messages`, `idor-media`, `idor-account`): user B
  can never read or change user A's chats, messages, media, reactions, stars, pins, polls, folders,
  drafts, scheduled messages, reports, sessions, push devices, lock, appearance or admin data.
  Outsiders always get 404, members without the right get 403, and a snapshot of every collection is
  unchanged afterwards. **No authorization bug was found.**
- **Production surface** (`production-surface.test.ts`): with `NODE_ENV=production` none of the
  `/v1/test/*` routes exist.

| ID  | Severity | Finding                                                                                                                                                                                                       | Status   |
| --- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| B1  | Medium   | The `/v1/auth/*` catch-all exposed all of Better Auth's own endpoints: `get-session` / `list-sessions` returned raw session tokens to scripts (defeating httpOnly), and two sign-in paths skipped our limits. | Fixed    |
| B2  | Medium   | No CSRF/origin check outside Better Auth's routes (SameSite=Lax still sends cookies from sibling subdomains; simple multipart posts pass CORS).                                                               | Fixed    |
| B3  | Low      | Log redaction missed top-level secrets and PINs, push keys, `AUTH_SECRET`, `VAPID_PRIVATE_KEY`.                                                                                                               | Fixed    |
| B4  | Low      | Access-log URLs carried signed-media signatures and invite codes.                                                                                                                                             | Fixed    |
| B5  | Low      | Subscribing with someone else's push endpoint moves it to the caller (by design for shared browsers; endpoints are never returned).                                                                           | Accepted |
| B6  | Low      | `ACCOUNT_DEACTIVATED` on an OTP request reveals a deactivated account (required by the auth rules).                                                                                                           | Accepted |
| B7  | Info     | Signed media links are 15-minute bearer URLs, bound to one file and purpose, masked in logs.                                                                                                                  | Accepted |
| B8  | Info     | Link-preview images can be fetched by any signed-in user (public web content, random ids).                                                                                                                    | Accepted |
| B9  | Info     | `/v1/health` and `/v1/ready` are public (container probes; no hosts or errors).                                                                                                                               | Accepted |
| B10 | Info     | Requests with neither `Origin` nor `Sec-Fetch-Site` are allowed (non-browser clients; they still need a session).                                                                                             | Accepted |
| B11 | Info     | Per-IP limits exempt loopback; `trustProxy` is loopback + private ranges, so it can't be spoofed.                                                                                                             | Accepted |
| B12 | Info     | A simultaneous burst against a rate-limited route is refused entirely by the in-memory limiter (errs on refusing).                                                                                            | Accepted |

**Origin check (B2):** every POST/PUT/PATCH/DELETE whose `Origin` is not `APP_URL` or one of
`CORS_ORIGINS` (also `Origin: null`) gets 403; without `Origin`, `Sec-Fetch-Site: cross-site` or
`same-site` is refused too. It runs in `onRequest`, before authentication
(`backend/src/plugins/origin-check.ts`). The Socket.IO handshake already refused foreign origins.
